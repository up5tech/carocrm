## Phase 7A completion — internationalization (PLAN §41)

- Completed the Phase 7A i18n feature set and fixed the blocking defect that made the `i18n.test.ts` suite order-dependent/flaky (4 then 2 then 1 failures across runs).
- Root cause: `RequestContextMiddleware` wrote `scope.acceptLanguage` (an `AsyncLocalStorage`-backed `RequestScope` value) *before* calling `scope.run(request.id, next)`. The write landed on the shared `fallback` store, and the fresh per-request store created by `run` had no `acceptLanguage`, so `I18nController`/`MetadataController` always saw `undefined` and fell through to the instance default (`en`). Fixed by setting `acceptLanguage` inside the `scope.run` callback so it lands on the per-request store. The core `createRequestContext`/`runWithRequestContextAsync` path (used by the error filter) was already correct.
- Also: made `GET /api/v1/I18n` `@Public()` so the SPA can restore the locale and paint the sign-in page pre-auth (§41.4) — it only exposes translation strings + public instance locale/timezone, never a user's own locale. Hardened the SPA boot in `main.tsx` to render first (`initI18nFromCache`, network-free) then reconcile with `initI18n()` in the background, so a first visit with no cached catalog and no token never blocks/aborts mounting. Corrected the `PreferencesSchema` Zod (`.nullable().optional()` for `exactOptionalPropertyTypes`) and `updatePreferences` typing; `null` clears locale/timezone back to the instance default.
- Verification: `pnpm -r build`, root+web typecheck, ESLint (autofixed one import-sort), and the i18n + request-scope + auth + metadata-api suites all green; i18n suite passes deterministically across repeated runs. Tests run against the configured project DB per AGENTS.md §3 (no extra DB).
