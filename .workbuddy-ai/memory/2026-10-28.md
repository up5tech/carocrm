## Phase 22.7 — Idempotency, Outbox/Inbox, and Retry Hardening (implemented)
- Deliverable: `docs/quality/phase-22-idempotency-retry.md` (inventory of every high-risk operation with its idempotency key + enforcing constraint + strategy + retention; the required-scenario matrix; 5 defects; the replay contract; retry-policy facts; acceptance) + `docs/quality/known-gaps.md` extended to G23.
- Core finding: NOTHING is delivered exactly once. Every operation is either **at-least-once + a durable dedup key** or **at-most-once by claim** (claim under a unique constraint, loser replays the stored answer). Which one applies is a property of the operation, not the transport — now written down per operation.
- Fixed F1 (Medium): marketing webhook door looked the dedup key up BEFORE verifying the signature → a forged delivery reusing a known key was answered "duplicate" (an oracle) and could occupy the genuine key. Now: verification first, and a rejection is recorded under `rejected:<sha256(provider|dedupKey|payload)>` (the anti-poisoning rule the voice door already used).
- Fixed F2 (Medium): marketing door claimed the key with SELECT-then-INSERT → two concurrent deliveries of the same event both decided they were first, the loser answered 500. Now the INSERT is the claim (`on conflict do nothing`) and the loser re-reads the winner's row.
- Fixed F3 (**High, money**): `PaymentProviderEventLog.providerEventId` had NO unique constraint → two concurrent deliveries could settle a payment request twice. Migration `083_phase22_payment_provider_event_dedup.sql` adds a UNIQUE partial index on `attrs->>'providerEventId'`; the service claims by inserting and answers the loser as the duplicate. (Table had 0 rows in the dev DB, so the index applied cleanly.)
- Fixed F4 (Low): the connector webhook door answered a delivery that FAILED verification with 202 while its own comment said 401 → providers retried a signature that fails forever. Now 401 (`@Res()` + `reply.status`, the same pattern as the esignature webhook door).
- Fixed F5 (Medium): the retention purge DELETED the rows carrying the dedup keys (`integration_webhook_deliveries` 14d, `integration_sync_operations` 30d) → a provider redelivering after the window was applied again, the opposite of the module's own comment ("only the payload it goes"). Now the purge clears the payload and keeps the row.
- New tests: `apps/api/test/phase22-replay-contract.test.ts` (8 — marketing replay/forged-key/concurrent/same-key-different-body, connector replay + 401, payment concurrent settle) and `apps/api/test/phase22-out-of-order-events.test.ts` (3 — a completed voice call stays completed when an older event arrives later, one receipt per delivery, one session per call).
- Out-of-order proven END-TO-END for Voice (signed callback → durable receipt → worker-authorised processing route → stored session). The ESignature equivalent stays at the pure-mapper level (the HTTP fixture is heavy) → noted as a remaining gap.
- Required scenarios (plan §12): 7/7 now either proven or recorded as a gap. "Same key, different body" is safe everywhere but NOT detected anywhere (3 doors store a body hash and never compare it) → G19.
- Remaining gaps recorded (G11–G23): no jitter on queue/outbox retry (G15), `JOB_BACKOFF_BASE_MS` is dead config (G16), no projection compares an event timestamp (G18), `jobs`/`job_logs` have no retention (G14), no operator API to retry/discard a failed job (G21), `outstandingJob` filters a status ('active') that never exists → misses a RUNNING job (G22), the dead-letter replay route has no capability check (G11) and does not re-run the work (G23).
- DB discipline: only the configured primary DB; the one migration is additive and was reviewed before it was applied; no destructive command; every new row is deleted by exact id / run marker.

## Phase 22.8 — Journey: lead acquisition, scoring, qualification, conversion (implemented)
- Deliverable: `docs/quality/phase-22-journey-lead-to-customer.md` (preconditions/capabilities, actors, test-owned data, the 12 steps, persisted state + events, audit, dedup, cleanup, evidence, limitations, acceptance) + `apps/api/test/phase22-journey-lead-to-customer.test.ts` (12 ordered steps) + `docs/quality/known-gaps.md` G24/G25.
- The journey in one line: a Lead arrives → the active model scores it (30/Cold) → a campaign `opened` signal in `marketing_events` moves it (70/Hot) → a direct field change moves it again (90/**Sales Ready**) → and **nothing happens**: no conversion, no Contact/Account/Opportunity, no access. Only an explicit preview+convert creates the identities, and only then can Sales create a quote against the converted Account.
- The negative assertion (plan §13.1 step 5) had never been proven: a qualified band does not change `Lead.status` (there is no 'Qualified' value in the enum — qualification IS the derived `scoreBand`), does not create any record, and does not grant access. The only allowed reaction is the `leadScore.bandChanged.v1` event.
- Cross-module hand-off proven: `POST /api/v1/Sales/document` (kind quote) with `data.accountId = Lead.convertedAccountId` → 201, the quote's header carries that Account. The conversion writes NO selling semantics — `Opportunity.stage = Qualification`, `amount` null.
- Disclosure policy proven with two different denials: a caller with no LeadScore right gets 403 AUTHORIZATION_DENIED on the convert command, but 404 (missing, not forbidden) on the converted Contact — because the role has `read: own` and the record is not theirs.
- Findings: F1 — there is no qualification *state*, only the derived band (Info). F2 — no first-class campaign↔Lead link; the Lead has only the free-text `source`, the campaign association lives in `marketing_events` / `MarketingConsent.campaignId` / `TargetListEntry` / the journey enrollment (G25). F3 — **the marketing form's Lead write is silently truncated**: `MarketingFormService.createLead` writes `companyName`, `utmSource`, `utmMedium`, `utmCampaign`, `campaignId`, `formIntakeKey`, and NONE of them is a Lead field, so `EntityCrudService.prepareWrite` deletes them → the company is lost, the campaign reference never lands, and the form's intake-key idempotency can never match (G24).
- G24/G25 deferred to 22.12 (the marketing journey owns that path). The Lead-metadata fix is additive (attrs are JSONB, no migration), but it belongs with the module that writes those fields.
- Nothing else was changed: no product code in this sub-phase — the journey proves the implemented behaviour, and where the behaviour is wrong it is recorded rather than patched.
