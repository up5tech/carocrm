## Fixed: drag & drop in the Kanban board (and Plan view) never worked

User report: "cho phép user kéo thả items trong project board". Root cause was **not** a missing
feature — `DndContext`, `SortableContext`, `useDroppable`, `useSortable` and the `onDragEnd` →
`api.moveProjectTask(...)` wiring all existed. The defect: every draggable spread
`sortable.attributes` but **never `sortable.listeners`**. dnd-kit puts the `onPointerDown`/
`onKeyDown` handlers in `listeners`; `attributes` is ARIA/`role`/`tabIndex` only. So no drag could
start anywhere in the Projects UI (board *or* Plan view) — `grep -r listeners apps/web/src` returned
nothing.

Changes:
- `apps/web/src/pages/projects/ProjectBoardPage.tsx`: `BoardCard` gained an explicit drag handle
  (`setActivatorNodeRef` + `attributes` + `listeners`, `stopPropagation` on click, `disabled` when
  the user may not move) so clicking the card still opens the task; card title moved into a flex row
  with the handle (`minWidth: 0` keeps the ellipsis).
- Same file: the board gate changed from `capabilities.moveTask === true` to
  `moveTask === true || capabilities.isMember === true`. `moveTask` is project-wide only, so a plain
  Member (role `stageMoveScope: 'assigned'`) got `moveTask: false` and the handle was disabled for
  **every** card, including their own — even though the server accepts those moves. Members now get
  an enabled handle and the server refuses the cards they do not own (the board already refetches
  and snaps back, as its own doc comment says).
- `apps/web/src/pages/projects/ProjectPlanPage.tsx`: added the missing `{...sortable.listeners}` to
  the existing drag handle (same bug).
- `apps/web/src/styles/lizant.css`: `.lizant-project-drag-handle` gained `touch-action: none`
  (PointerSensor cannot take over touch gestures without it), `:active { cursor: grabbing }` and a
  `:disabled` style.
- `docs/modules/projects/README.md` + `docs/reference/alpha-status.md`: recorded the defect and fix.

## Fixed: dragged item occluded while crossing into another column/group

User report: "kéo từ start sang end tuy chưa thả chuột nhưng item kéo biến mất, thả chuột thì xuất
hiện trong end". Cause: the dragged card/row stayed a DOM child of its source container, so the
*following* containers — `.lizant-project-column` with opaque `background: #f7f9fb` on the board,
antd white group cards in the Plan view — painted over it as soon as it crossed their edge. It was
not clipping (neither container sets `overflow: hidden`). Canonical dnd-kit fix: `DragOverlay`.

Changes:
- `apps/web/src/pages/projects/ProjectBoardPage.tsx`: added `activeTask` state + `taskById()` helper;
  `DndContext` gained `onDragStart`/`onDragCancel` (clear `activeTask`); extracted `BoardCardContent`
  (task body, optional `dragHandle`) shared by `BoardCard` and the overlay; `<DragOverlay
  dropAnimation={null}>` renders the active card in a portal.
- `apps/web/src/pages/projects/ProjectPlanPage.tsx`: same treatment; new presentational
  `TaskRowOverlay` (row shape minus the transition buttons, since the overlay is not interactive).
- `apps/web/src/styles/lizant.css`: `.lizant-project-card.is-dragging` and
  `.lizant-project-task.is-dragging` are now `opacity: .45` placeholders (their old border/shadow
  moved to the new `.lizant-project-card-overlay` / `.lizant-project-task-overlay` lift styles);
  `.lizant-project-drag-handle` gained `font-family: inherit` so the overlay's `<span>` handle
  renders identically to the list's `<button>`.
- `dropAnimation={null}` on both overlays because both views refetch from the server on drop.
- Docs: `docs/modules/projects/README.md`, `docs/reference/alpha-status.md`.

Note: dnd-kit sets the overlay's width/height inline from the dragged node's rect, so no CSS width
is needed (an earlier `width: 242px` guess was removed).

## Added a generic board (Kanban) view for record lists — Opportunity included

User asked (vi): "làm board view cho Opportunity". Implemented as a **metadata-driven** view rather
than an Opportunity-specific page, so it follows AGENTS §8 ("do not hard-code the entire CRM schema
in frontend components") and any enum field on any entity gets a board.

- `apps/web/src/pages/EntityBoardPage.tsx` (new): one column per enum value of the group field,
  one card per record, drag between columns = `PATCH /:entity/:id` with `{ [groupBy]: value,
  version }`. Group field is selectable (default `stage` → `status`/`state` → first enum field);
  card body = the record's scalar `inList` fields (link/multi/text/password excluded, cap 3);
  card title links to the record. Per-column paging (25 + "Load more"), per-column `total` badge,
  text search via `/Search/:entity`, an empty-value column rendered only when it has rows.
  Uses `DragOverlay` (same occlusion lesson as the Projects board, see above) and
  `{...sortable.listeners}` on the drag handle (same defect class as the 2026-10-14 fix).
- `AppRoutes.tsx`: `/:entity/board` declared **before** `/:entity/:id` so "board" is not read as a
  record id. `EntityListPage.tsx`: a **Board** button in the header, rendered only when
  `boardGroupFields(definition)` is non-empty; the board page has the inverse **List** button.
- `state/metadata.ts`: new `boardGroupFields()`, `defaultBoardGroupField()`, `enumValues()`.
- `styles/lizant.css`: new labelled `.lizant-board-*` block (columns/cards/pills/handle) — copied
  values from the Lizant board rather than reusing `.lizant-project-*`, so the generic view does
  not depend on the Projects module's stylesheet.
- `i18n/{en,vi}/web.json`: new `web.board.*` section (11 keys).
- `docs/reference/alpha-status.md`: new section documenting the view, its limits and the
  no-verification caveat.

Design decisions worth keeping:
- **No backend change.** Columns are fetched with the existing list/`/Search` endpoints, one
  request per column (`where: [{field, operator: 'equals'|'isNull', value}]`), so the Query Engine,
  entity/record/field ACL, filters and audit are reused untouched. No migration, no seed.
- **No capability endpoint** exists for generic entities (only Projects has one), so the drag
  handle is always enabled and the server is the authority on whether a move is allowed; a refusal
  is surfaced and the board reloads.
- The `['stage','status','state']` preference list only picks the *default* column; it is a naming
  convention, not a schema hard-code, and every enum field stays selectable on the page.
