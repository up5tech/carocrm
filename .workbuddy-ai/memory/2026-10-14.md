## Fixed: drag & drop in the Kanban board (and Plan view) never worked

User report: "cho phép user kéo thả items trong project board". Root cause was **not** a missing
feature — `DndContext`, `SortableContext`, `useDroppable`, `useSortable` and the `onDragEnd` →
`api.moveProjectTask(...)` wiring all existed. The defect: every draggable spread
`sortable.attributes` but **never `sortable.listeners`**. dnd-kit puts the `onPointerDown`/
`onKeyDown` handlers in `listeners`; `attributes` is ARIA/`role`/`tabIndex` only. So no drag could
start anywhere in the Projects UI (board *or* Plan view) — `grep -r listeners apps/web/src` returned
nothing.

Changes:
- `apps/web/src/pages/projects/ProjectBoardPage.tsx`: `BoardCard` gained an explicit drag handle
  (`setActivatorNodeRef` + `attributes` + `listeners`, `stopPropagation` on click, `disabled` when
  the user may not move) so clicking the card still opens the task; card title moved into a flex row
  with the handle (`minWidth: 0` keeps the ellipsis).
- Same file: the board gate changed from `capabilities.moveTask === true` to
  `moveTask === true || capabilities.isMember === true`. `moveTask` is project-wide only, so a plain
  Member (role `stageMoveScope: 'assigned'`) got `moveTask: false` and the handle was disabled for
  **every** card, including their own — even though the server accepts those moves. Members now get
  an enabled handle and the server refuses the cards they do not own (the board already refetches
  and snaps back, as its own doc comment says).
- `apps/web/src/pages/projects/ProjectPlanPage.tsx`: added the missing `{...sortable.listeners}` to
  the existing drag handle (same bug).
- `apps/web/src/styles/lizant.css`: `.lizant-project-drag-handle` gained `touch-action: none`
  (PointerSensor cannot take over touch gestures without it), `:active { cursor: grabbing }` and a
  `:disabled` style.
- `docs/modules/projects/README.md` + `docs/reference/alpha-status.md`: recorded the defect and fix.

## i18n sweep — translated every hardcoded string in the SPA

User asked (vi): "check xem phần web có i18n nào chưa được dịch thì dịch nó". Chose scope **all web pages**.

Audit first: `i18n/{en,vi}/web.json` were already **in sync** (205 keys each) and no `t()` key used by the
SPA was missing. The real gap was the opposite direction — ~20 pages/components rendered **hardcoded
English** and never called `t()` at all (PLAN §41.1: "a hard-coded user-visible string is a defect").
The only genuine catalog gap anywhere was `core.common.reload` (missing in `vi`, and unused by the web).

### Infra fix (found while wiring placeholders)

`apps/web/src/state/i18n.ts` initialised i18next with its **default** `{{ }}` interpolation delimiters,
while the catalog (shared with the API, whose `interpolate()` uses single braces) writes `{count}`.
So **every existing interpolated key was broken in the SPA** — `t('web.list.deleteConfirm', {count})`
rendered a literal `{count}`. Fixed by setting `interpolation: { escapeValue: false, prefix: '{', suffix: '}' }`
in both `initI18n()` and `initI18nFromCache()`, aligning SPA and API on one catalog format.
New keys therefore use `{var}`. (Avoided naming any placeholder `count` — i18next treats it as the
plural selector.)

### Catalog

`i18n/{en,vi}/web.json` grew from 205 to **~470 keys** across 26 groups (was 6). New groups:
`login, home, search, portal, common, tasks, calendar, stream, dashboards, reports, admin, adminAudit,
adminExtensions, adminJobs, adminPortals, entityManager, entityAdmin, workflows, workflowEditor,
processes, processEditor, shell, params`. Plus `web.list.filtersAria`, `web.language.changeFailed`,
`web.login.failed`, `web.workflows.defaultActionName`, `web.processEditor.{defaultReject,defaultApproved,
defaultRejected,continuesAtPlaceholder}`. `vi/core.json` gained the missing `common.reload`.
Both `web.json` files are **structurally identical** (verified: same 26 groups closing on the same line
numbers, 942 lines each).

### Files wired to `t()` (23 touched)

New: LoginPage, HomePage, SearchPage, PortalHomePage, TasksPage, CalendarPage, StreamPage, StreamPanel,
DashletResult, DashboardsPage, ReportsPage, AdminAuditPage, AdminExtensionsPage, AdminJobsPage,
AdminPortalsPage, EntityManagerPage, EntityAdminPage, WorkflowsPage, WorkflowEditorPage, ProcessesPage,
ProcessEditorPage, ParamsEditor, AppShell (leftovers), `state/session.ts` (`'Login failed.'`).
Also leftovers in EntityListPage (`aria-label="Record filters"`).
Module-level constant label arrays became functions so they can call `t()`: `reportKinds()` (ReportsPage),
`levelOptions()` / `ruleActions()` (EntityAdminPage).

### Deliberate decisions

- **Data values were NOT translated**: enum/status codes rendered raw (`pending`, `Completed`, `Triage`,
  `Work`, project group types, entity names, `Milestone`, `FinishToStart`), and technical placeholders
  (`fieldName`, `system.cleanupOutbox`, `approved`, `assignedUserId`, `panelName`). Translating those
  would change stored/compared values, not chrome.
- **Defaults that ARE stored were translated** because they are user-editable labels: new workflow node
  name, new process user-task/outcome/end names, new gateway name, new answer label. (A vi user creating
  a node now stores "Duyệt" — acceptable, the name is editable and the `value` slug is unaffected.)
- **Inline markup dropped** in three hint paragraphs (`<code>EXTENSIONS_DIR</code>`, `<em>available</em>/
  <em>installed</em>`, workflow `<strong>published</strong>`, the formula `<code>field('x')</code>` hints):
  kept as one translatable key instead of splitting a sentence into fragments, which would force English
  word order on Vietnamese. Text content preserved; only the emphasis styling is gone.
- `web.params.userId` / `web.params.emailTo` keep the literal `{{assignedUserId}}` / `{{emailAddress}}`
  hints — i18next leaves an unknown interpolation untouched, and server-side `interpolate()` is a no-op
  when no variables are passed.

## Follow-up bug: UI showed raw keys (`web.login.submit`) instead of translations

User reported the sign-in screen rendering `web.login.subtitle` / `userName` / `password` / `submit`
verbatim. Root cause was **not** the catalog — it was that **nothing ever re-renders the React tree
when the catalog arrives**.

`apps/web/src/state/i18n.ts` exports a plain `t()` (not a hook) and **no file subscribes to i18next**
(`grep useTranslation|languageChanged|useSyncExternalStore` → nothing). So a screen painted before the
catalog lands keeps its raw keys forever. The sign-in page is the only screen affected in practice
because it is the *first* paint: `main.tsx` deliberately renders before/without waiting for
`GET /I18n` (§41.4), and `AppRoutes`' `loadPrincipal()` fires `set({ restored: true })` first — which
re-renders `LoginPage` (it subscribes to the zustand session store) *before* the catalog request
resolves — so the last render that happens has no resources yet. Every other page is reached by
navigation long after `initI18n()` finished, which is why the defect was invisible until the login
page started calling `t()`.

### Fix — `apps/web/src/main.tsx`

Hoisted `createRoot()` out of `render()` (calling it twice on the same container logs a React warning)
and made `render()` re-render the existing root, then:
`i18n.on('languageChanged', render)` plus `void initI18n().catch(...).finally(render)`.
The explicit `finally(render)` is the load-bearing part: on the cached/unchanged path the language
never actually changes, so `languageChanged` may not fire.

### Fix — `apps/web/src/components/AppShell.tsx`

Both `navItems` memos translate at build time, so a language switch would have repainted the page but
left the sidebar in the old language. Added `activeLocaleName()` to their dep arrays (imported it).

### ALSO REQUIRED — restart the API

`I18nService.ensureCatalogs()` caches `this.catalogs` for the **process lifetime** (loaded lazily on
the first `catalogFor`/`translate`/error-filter call, from `process.cwd()/i18n`). Editing
`i18n/*.json` therefore changes nothing until the API restarts — Vite HMR reloads the SPA, but the API
keeps serving the catalog it read at boot. This is the second half of the reported symptom and is an
operational step, not a code bug. A dev-friendly mtime-based reload in `ensureCatalogs()` was
considered and **deliberately not added** (unrequested API behaviour change, unverifiable without a
shell); offered to the user as a follow-up.

### Catalog validated (no shell, so by inspection)

- 29 groups; each file has exactly **29 key lines without a trailing comma** — one per group, i.e. the
  last key of each group — and the 29 line numbers match between `en` and `vi` exactly.
- No key violates `KEY_RE`: no key line contains a hyphen/space/non-word char, none starts a segment
  with a digit or underscore.
- All 10 lines containing `\"` (escaped quotes) are balanced and line-for-line identical across locales.
- `GET /api/v1/I18n` is `@Public()` (`i18n.controller.ts`), so the pre-auth fetch is not the problem.

## ROOT CAUSE (the real one): the dev API never found `i18n/` at all

User: "vẫn lỗi đó". The re-render fix was necessary but **not sufficient** — the catalog was never
being loaded by the dev server.

`I18nService` had `private sourceDir = process.env.I18N_DIR ?? join(process.cwd(), 'i18n')`, and
`process.cwd()` is **not** the repository root under `pnpm dev`:

| launch | cwd | `cwd/i18n` | result |
| --- | --- | --- | --- |
| `pnpm dev` / `dev:all` → `pnpm -r --filter @carocrm/api dev` → `tsx watch src/main.ts` | `apps/api` | **missing** | translation disabled |
| Playwright `webServer` → `node apps/api/dist/main.js` | repo root | found | works |
| `scripts/e2e-smoke.sh` (`cd "$(dirname "$0")/.."`) | repo root | found | works |
| `vitest` (`apps/api/test/i18n.test.ts`) | repo root | found | works |

Corroboration that pnpm runs the script in the package dir: the script itself is `tsx watch src/main.ts`
— a package-relative path that only exists under `apps/api`.

With `sourceDir` missing, `ensureCatalogs()` takes the `existsSync` early-return branch
(`log.warn('i18n catalog directory is missing; translation disabled')`, `this.locales = []`, empty
catalog map), so `translate()` returns `undefined` for **every** key and the SPA's `t()` falls back to
returning the key. Hence raw keys on every screen — which is also what the user's original request
("check i18n nào chưa được dịch") was really describing, not merely leftover English.

**Every test passed anyway** because all four harnesses above run from the repo root. Nothing exercised
the `pnpm dev` launch mode, so the defect was invisible to CI.

### Fix — `apps/api/src/i18n/i18n.service.ts`

Added `resolveCatalogDir()`: `I18N_DIR` still wins, otherwise walk up from `cwd` (max 4 levels, same
shape as `loadDotEnv()` in `config.ts`) until a directory containing `i18n/` is found, falling back to
`join(cwd, 'i18n')` so the existing "directory is missing" warning still fires when there truly is no
catalog. `sourceDir` now uses it. Also fixed a missing space in the `node:fs` import
(`readdirSync,readFileSync` → `readdirSync, readFileSync`) — a pre-existing prettier violation.

Note `join` is still used by `ensureCatalogs()`; `resolve` was added to the same import.

### Where things stand

Three independent defects stacked on this one symptom, all now fixed:
1. API never located the catalog under `pnpm dev` (this entry) — the dominant cause.
2. SPA never re-rendered when the catalog arrived (earlier entry) — would have kept the *sign-in* page
   raw even after (1).
3. Sidebar `navItems` memos not keyed on the locale (earlier entry).

Editing `i18n/*.json` still requires an API restart, but editing `src/**` does not: `tsx watch` restarts
on this change, so the fix takes effect on save. A mtime-based catalog reload in `ensureCatalogs()` was
again considered and left out (unrequested API behaviour change, unverifiable here).

**Not verified** — no shell. In particular the fix has not been exercised by booting `pnpm dev`; the
proof is static (cwd table above). If it still fails, the next check is the API boot log for
`i18n catalogs loaded { locales, dir }` vs `i18n catalog directory is missing`.
