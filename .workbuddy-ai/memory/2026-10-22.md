# 2026-10-22

## BPM participant UI (Phase 16 gap closed)

The process engine was participant-facing server-side but had no UI for non-admins: only
`/admin/processes` and `/tasks` existed, and nothing could *start* an approval from a record.

API (`apps/api/src/processes/`):
- `GET /api/v1/Process/action/available?entityType=` — participant-facing start menu (published +
  enabled + `entity_type in (type, '*')`), identity/description only, never nodes/actions.
- `GET /ProcessInstance?entityType=&entityId=` — record-scoped list; half a filter is a 422.
- `instanceParticipantClause` now includes `i.initiated_by` — it previously disagreed with
  `maySeeInstance`, so an initiator's own approval vanished from lists once the token moved on.

Web:
- `components/ProcessPanel.tsx` on the record detail page (start dropdown, per-record history,
  cancel for starter/admin), `components/ProcessTrailModal.tsx` (shared trail, also used by the
  admin instances tab), `pages/MyProcessesPage.tsx` at `/processes` + nav seed `myProcesses`
  (`core.app.myProcesses`), i18n `web.recordProcess.*` / `web.myProcesses.*` in en + vi.
- Verified in a headless browser against a live stack (screenshots in /tmp): panel, start → trail,
  my-approvals list, admin instances tab.

Gotchas found:
- A stale `tsx watch` API on :3030 silently serves old routes (the port is occupied, the new
  process logs "listening" then fails to bind). Restart the dev API after adding a route.
- The dev API rate-limits bursts (`@fastify/rate-limit`), surfacing as 500s on `/Navigation`,
  `/Settings`, `/ProcessInstance` — wait ~30s, it is not a code fault.
- `pnpm --filter @carocrm/web build` fails in this sandbox at `emptyDir(dist)` (bulk-delete guard);
  `vite build --outDir /tmp/...` works and is the way to check the bundle.

## Sidebar owns its own scroll

The rail was a stretched flex child of the page row, so it grew to the full document height
(measured 2945px on `/home`) and `.carocrm-sider-scroll` never overflowed — the menu rode along
with the page instead of scrolling inside the rail.

`apps/web/src/styles/carocrm.css`:
- Desktop only (`@media (min-width: 769px)`): `.carocrm-sider` is now `position: sticky; top: 70px;
  height: calc(100vh - 70px); align-self: flex-start; overflow: hidden` — the rail pins under the
  sticky header and the inner box gets a real height to overflow against.
- `.carocrm-sider-scroll` gained `min-height: 0` (the declaration that actually lets a flex child
  shrink), `overscroll-behavior: contain` and a thin 6px scrollbar.
- Narrow viewports untouched: the drawer is `position: fixed; top: 0; bottom: 0` and already
  scrolled internally; the desktop rule must stay out of that block or the height wins over
  `top/bottom`.

Verified headless (1440x900, 1440x500, 390x844): rail 830px tall at top 70, menu 806/1451
scrollable, window scroll to 600 leaves the rail pinned and the menu's own `scrollTop` intact,
collapsed 72px rail identical, phone drawer fixed full-height with `overflow-y: auto`.

The vite dev server on :8080 had a stale transform cache — it kept serving the old CSS after the
edit and after a `touch`, so verification ran on a second server (`VITE_PORT=8181`).
