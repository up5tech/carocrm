# Production installation and upgrade

> **Status:** deployment artifacts and operator procedure are provided by Phase 24.3. This repository
> does not contain production credentials, a secret manager, TLS certificates, or an approved recovery
> target. The procedure has **not** been exercised against a recoverable deployment; production remains
> NO-GO until the Phase 23 release blockers and the checks in this runbook are closed.
>
> CaroCRM is single-tenant: use a separate database, Redis, worker, file store, secrets and backup set
> for each installation. Never share these resources across customer organisations.

## Topology and artifacts

- `docker/production.Dockerfile` builds API, one-shot migration, worker and static SPA images.
- `docker-compose.production.yml` runs PostgreSQL, authenticated Redis, API, worker and SPA on one
  private Compose network. Only the SPA edge port is published, bound to loopback by default.
- Put a trusted TLS reverse proxy in front of that loopback port. It must redirect HTTP to HTTPS,
  set HSTS, overwrite `X-Forwarded-For` and `X-Forwarded-Proto` (the latter to `https`), and must be
  the only path to the application. The Compose topology assigns the SPA edge `172.30.0.10` on its
  private network and configures the API to trust only `172.30.0.10/32`. Never publish API, PostgreSQL
  or Redis ports.
- Nginx serves the built SPA with CSP, `nosniff`, `Referrer-Policy`, and a health endpoint. The TLS
  terminator owns HSTS and certificate policy.
- Runtime `DATABASE_URL` must use an application role with DML only. `MIGRATIONS_DATABASE_URL` is
  supplied only to the one-shot migration service and uses the separate DDL-capable migrator role.
  `scripts/deploy/provision-postgres-roles.sql` interactively provisions those roles for a selected
  fresh dedicated database; run it as that database's owner and enter unique generated passwords
  through its hidden prompts. For an existing database, a reviewed ownership transition is required
  before the migration role can alter objects owned by the prior role. Do not pass the bootstrap/admin
  URL to API or worker.
- No seed is run in these images. Provision the first administrator and system roles through a
  separately reviewed bootstrap procedure for the target installation; never use development admin
  credentials in production.

## Prerequisites

1. A supported Docker Engine / Compose v2 host, durable encrypted storage and outbound network rules.
2. A DNS name and trusted TLS reverse proxy in front of the loopback-bound SPA edge.
3. A dedicated installation PostgreSQL database and least-privilege roles, plus private authenticated
   Redis. Do not point this stack at another customer's shared services.
4. A secret manager, or a root-owned environment file readable only by the operator (mode `0600`).
   Never commit or bake the file into an image. Values must be generated by the operator; do not copy
   development values from `.env.example`.
5. A reviewed backup and recovery plan per `docs/security/deployment-baseline.md` and
   `docs/security/exception-register.md`. The existing G80/G81 blockers still prevent production GO.

Required environment keys (values omitted intentionally):

```text
POSTGRES_DB
POSTGRES_BOOTSTRAP_USER
POSTGRES_BOOTSTRAP_PASSWORD
REDIS_PASSWORD
DATABASE_URL
MIGRATIONS_DATABASE_URL
REDIS_URL
JWT_SECRET
ENCRYPTION_KEY
CORS_ORIGINS
```

`JWT_SECRET` must be unique and strong; `ENCRYPTION_KEY` must be 64 hexadecimal characters. Set
`CORS_ORIGINS` to explicit HTTPS SPA origins only. The Compose API trusts only the fixed SPA-edge address;
keep the private network isolated from untrusted containers. Optional provider settings should remain
unset until configured.
The production guards reject the known JWT/database defaults, weak/empty encryption key, wildcard CORS,
non-enforced extension trust and API auto-migration.

## First installation

1. Build and tag a reviewed release commit. Pin immutable `CAROCRM_API_IMAGE`,
   `CAROCRM_MIGRATION_IMAGE`, `CAROCRM_WORKER_IMAGE` and `CAROCRM_WEB_IMAGE` tags in the deployment
   environment. The API and migration images are separate targets: the migration image defaults to
   the one-shot migration command, while API starts the server. Review image provenance and scan
   results before deployment.
2. Install the operator's environment through the secret manager or protected env file. Keep
   `EDGE_BIND_ADDRESS=127.0.0.1`; a local TLS terminator can reach this port. For a remote TLS
   terminator, use a firewall-restricted private address and review the proxy trust topology before
   changing network configuration. The external TLS proxy must be the only public ingress.
3. Start only the database and Redis services and wait for their health checks:

   ```sh
   docker compose --env-file /secure/path/carocrm.env -f docker-compose.production.yml up -d postgres redis
   ```

4. Apply the additive, version-controlled kernel migration chain once with the migrator role. The
   Compose migration target is built from the same reviewed commit as the API; pin its immutable
   release tag before running this command:

   ```sh
   docker compose --env-file /secure/path/carocrm.env -f docker-compose.production.yml --profile upgrade run --rm migrate
   ```

   The migration process uses `schema_migrations`; it does not seed users or reset the database. A
   failed migration stops the rollout. Preserve logs and diagnose the failed migration; do not edit
   migration history, rerun destructive cleanup, or use a reset command.
5. Start API, worker and SPA; the API has `AUTO_MIGRATE=false` and will fail closed rather than apply
   DDL with its runtime role:

   ```sh
   docker compose --env-file /secure/path/carocrm.env -f docker-compose.production.yml up -d api worker web
   docker compose --env-file /secure/path/carocrm.env -f docker-compose.production.yml ps
   ```

6. Configure the external proxy to forward HTTPS to the loopback SPA port. It must overwrite, not
   append client-supplied forwarded headers. Verify redirect, certificate, TLS policy, HSTS and the
   secure cookie behavior through the public HTTPS URL.
7. Provision the initial administrator using the approved installation bootstrap procedure. Do not
   run `pnpm db:seed` as a production shortcut; that command deliberately refuses production mode.
8. Run the targeted post-install smoke from an operator workstation using a dedicated smoke-test
   administrator:

   ```sh
   SMOKE_BASE_URL=https://crm.example.invalid \
   SMOKE_ADMIN_LOGIN=AGENT_TEST_install_smoke \
   SMOKE_ADMIN_PASSWORD='(injected privately by the operator)' \
   bash scripts/production-install-smoke.sh
   ```

   It verifies HTTPS readiness, authentication and `Secure` cookies, metadata, account create/read/
   update/soft-delete, and a `system.noop` job completed by the worker. It creates only one uniquely
   marked account and one job, cleans them up by returned IDs, and never seeds or applies migrations.
   It does not exercise every provider or prove backup/restore. Use a dedicated test user; do not run
   against customer records.

## Upgrade

1. Review release notes and every pending SQL migration. Confirm they are additive/backward-compatible;
   Phase 24.3 does not authorize destructive schema changes.
2. Verify a current encrypted backup and its off-host copy before changing images. A backup freshness
   check alone is not a restore drill. Do not proceed with real customer data while G80/G81 remains
   blocked or without the explicit recovery approval required by the release decision.
3. Pin and stage the new API/migration/worker/web images. Pause queue consumption and API writes during
   the migration window:

   ```sh
   docker compose --env-file /secure/path/carocrm.env -f docker-compose.production.yml stop worker api
   ```

4. Apply migrations with the new release's migration image tag, built from the same reviewed commit
   as API/worker/web:

   ```sh
   docker compose --env-file /secure/path/carocrm.env -f docker-compose.production.yml --profile upgrade run --rm migrate
   ```

5. Start the API first, wait for `/health/ready`, then start worker and web. Resume the external TLS
   route only after the public HTTPS smoke succeeds.
6. Run `scripts/production-install-smoke.sh`, inspect worker/API health and logs, confirm scheduled
   jobs/outbox processing resumes, and record image digests, migration names and results in the
   installation change record. Do not include secrets or database URLs in that record.

## Rollback limits

- Before applying migrations, rollback means restoring the previous immutable image tags and restarting
  the old services.
- After an additive migration, rollback to the previous application image is allowed only if the
  migration was reviewed as backward-compatible with that version. Otherwise stop and follow the
  tested recovery plan; do not attempt an improvised down migration.
- Never downgrade by deleting columns/tables, rewriting `schema_migrations`, restoring over the primary
  database without approval, or deleting Compose volumes. A database restore requires the separately
  approved recovery target and procedure; see `docs/security/deployment-baseline.md` §6 and the G80/G81
  exception records.
- Keep API and worker versions aligned. Do not resume workers against an incompatible schema or queue
  contract.

## Verification and operational boundaries

- `GET /health/live` proves only that the API process responds; `GET /health/ready` also checks the
  database. The worker has no public health listener; verify its container state and job completion.
- Verify PostgreSQL and Redis have no published ports, the runtime DB role cannot create tables, and
  the migration URL is absent from API/worker containers. Check file/backup permissions and off-host
  backup freshness independently.
- All resources and scaling remain installation-local. Do not connect one installation to another
  customer's database, Redis queue, worker, file store, encryption key or backup destination.
- `docker-compose.yml` remains development-only. Do not edit it into a production deployment or use
  its credentials, seeding behavior or source bind mount in production.
