## 1. What Phase 24 is

Phase 24 sequences the P0/P1/P2 recommendations of the system review into sub-phases 24.0–24.12:
ratify the single-tenant boundary, close the Phase 23 NO-GO blockers, ship a production
install/upgrade path, complete the machine-checked API contract, make release documentation
truthful, then deliver inbound mail, bounded email/calendar sync, outbound events, provider sandbox
evidence, UX completion and a final go/no-go.

**Product boundary (owner decision, 2026-11-13):** one deployment serves one customer organisation.
There is no tenant id, tenant predicate, tenant-scoped session/API key or per-tenant schema, and no
such work is scheduled. `tenantRef` in the advanced-integrations connector is a provider-account
label, not an isolation field. See `docs/reference/product-charter.md` and
`docs/security/tenancy-decision.md`.

## 3. Behaviour changes a reader can notice

- **Single tenancy is now written as a boundary, not a gap.** README, the compatibility matrix and
  the alpha status say plainly that one deployment = one organisation, and the dead `tenantId`
  plumbing is gone from core context, ACL types and the logger.
- **A production topology exists on paper and in artifacts.** `docker-compose.production.yml` +
  `docker/production.Dockerfile` build non-root API/worker/SPA/migrate images; the runbook
  `docs/runbooks/installation-and-upgrade.md` is the operator procedure. Nothing has been deployed
  or recovered, so this is **not** production evidence.
- **Release facts are corrected.** The README no longer claims migrations stop at `070` (the tree
  is at `095`), and the in-app handbook's release-notes page names the Phase 23 note as the newest.
- **Mail can be collected.** With an inbound provider configured, `POST /api/v1/Email/action/pollInbound`
  turns a mailbox into `Email` records — once per message, per mailbox. Without one, the call fails
  clearly instead of pretending to collect mail. Administrators manage the mailboxes under
  `EmailAccount/action/inbound-connections`; the credentials are write-only and encrypted at rest.
- **Inbound email and calendar are collected installation-wide (Phase 24.7).** The Phase 24.6 mail
  collection is now wrapped in the Phase 24.7 sync scope: one or more installation-administered
  mailboxes or calendars (personal or shared) inside the organisation, each with its own owner,
  credential scope, mailbox/calendar cursor and record/field ACL; inbound calendar events (Google
  full + incremental, Microsoft Graph delta + webhook); personal connections writing as their owner;
  inbound records linked through the existing sync engine. Opt-in: an unconfigured installation fails
  clearly and no provider is enabled by default.

## 4. Migration requirements

Phase 24.0–24.5 added **no** migrations. Phase 24.6 added **one**:
`095_inbound_mail_connections.sql` (the `inbound_mail_connections` and `inbound_mail_cursors` tables
plus a scoped-dedupe expression index). Phase 24.7 added **one**: `096_phase24_7_sync_metadata.sql`
— additive metadata for the delivered scope (`Call.location` and `Meeting.location` so a synced
calendar event keeps its place, plus the Phase 24.6 inbound-mail fields). The current tree is 96
files, highest `096_phase24_7_sync_metadata.sql`; see the Phase 23 note §2 for the 089–094 changes.

## 5. Release decision

**NO-GO for production — unchanged.** The blockers are the same owner/deployment decisions recorded
in Phase 23.11 and carried into Phase 24.2:

- **G80/G81** — restore drill blocked (no approved isolated target, RPO/RTO; decision D4) and no
  installed encrypted off-host backup. 24.3 shipped the topology, not the backup or the drill.
- **Distribution** — no `LICENSE`, no recorded clean-room/AGPL owner outcome.
- **Exceptions** — the High/Critical rows in `docs/security/exception-register.md` §5 remain
  **unsigned**; the coding agent may not accept them.
- **Contract** — `api-spec/` is not yet `--strict`-green (24.4 in flight); the served OpenAPI
  document remains a route inventory (G1, D3 disposition awaiting sign-off).

A conditional alpha/pilot remains possible only under the Phase 23 review §8 conditions.

## 6. Known limitations

- Production artifacts are build-validated only; TLS proxy, secret injection, first-admin bootstrap
  and backup/restore are operator steps with no executed evidence.
- `api-spec/` covers 63 of 915 routes; strict mode is not enabled and the typed client
  (`packages/api-client`) is still a placeholder.
- Inbound mail and calendar sync are delivered but not exercised against a live provider mailbox or
  calendar; Google Calendar push, SES/SendGrid/Microsoft Graph send and the email UI remain unbuilt
  (D5 scope).
- CI stays nightly-only (G78, standing owner decision); SAML/SCIM stay deferred.
