# CaroCRM — Phase 23 security hardening release notes

> **Date:** 2026-11-13
> **Scope:** the Phase 23 security workstream (`plans/PLAN_Phase_23_Security_Hardening.md`), not a feature
> release and **not** a claim of complete EspoCRM parity. Only the verified scope below is claimed.
> **Release decision:** **NO-GO for production** — see
> [`docs/quality/phase-23-security-release-review.md`](../quality/phase-23-security-release-review.md).

## 1. Behaviour changes

### Authentication and sessions

- Failed logins are throttled per source and locked out per account, without revealing whether an account
  exists (`AUTHENTICATION_FAILED`), and the lockout is auditable (23.2).
- Self-service password reset exists: `POST /PasswordReset` and `POST /PasswordReset/confirm`, single-use,
  expiring and rate-limited; a successful reset revokes the account's sessions. The admin reset route is
  unchanged (23.2).
- MFA is **enforceable** per instance policy (`security.mfa.required`: `off` / `admins` / `all`). A user under
  the policy cannot obtain a usable session without the challenge; enrollment has an explicit pending state (23.2).
- Sessions can be listed and revoked (`GET /AppUser/me/sessions`, `DELETE /AppUser/me/sessions/:id`); refresh
  families detect reuse and revoke the family (23.2).
- API keys rotate (`POST /ApiKey/:keyId/rotate`), carry `last_used_at`, optional `read`/`write` scopes and
  optional IP/CIDR restrictions; only the hash is stored and the secret is shown once (23.2).
- Generic OpenID Connect sign-in is built as **configuration, not code** (`OIDC_PROFILES`): single-use hashed
  state, nonce, PKCE S256, exact redirect-URI comparison before the code exchange, `jose` id_token verification
  (RS/PS/ES only) and the same session issuance as password sign-in. SAML and SCIM remain deferred (23.3).

### Authorization and data access

- User-requested asynchronous work re-derives its principal at execution (`runAsUser`) and fails closed when the
  user is inactive; system-scoped jobs are enumerated and justified (23.4).
- Every explicit `403` writes a redacted `denied` audit row with actor, target, action and correlation id (23.4).
- Audit history resolves the record through the entity ACL, so a foreign record's field history is no longer
  readable by id (G96); attachments are denied independently of the parent endpoint (23.4/23.6).
- Attachment reads always require the parent record's ACL; the permissive standalone default is gone. API keys
  need `read`/`write` scope and may upload only to a record they can read (23.6).
- CSV export blanks a read-denied column and neutralises formula-leading values in every cell; global and entity
  search apply the same field ACL (23.10).

### Untrusted input, files and supply chain

- One shared SSRF classifier covers every outbound URL path; an empty allowlist refuses every fetch and the one
  redirect-following fetch is pinned (G86, 23.5).
- Marketing webhooks verify HMAC-SHA256 over `timestamp.rawBody` with a mandatory timestamp; stale, unsigned,
  duplicate and malformed deliveries are refused before any state change (G33, 23.5).
- Extension packages are verified with an Ed25519 signature over a canonical digest of every file, against
  `EXTENSION_TRUSTED_KEYS`; `EXTENSION_TRUST_MODE` must be `enforce` in production (23.6).
- File validation requires real PDF/ZIP/legacy-Office magic numbers, closing the "executable under
  `application/pdf`" path (23.6).

### Configuration, retention and operations

- CORS fails closed when `CORS_ORIGINS` is unset; CSRF tokens are `crypto`-backed and compared in constant time;
  API-key secrets are compared with a length-checked `timingSafeEqual` (23.1).
- Production boot refuses the development JWT secret, the compose placeholder `change-me-in-production`, an empty
  `ENCRYPTION_KEY`, a non-`enforce` extension trust mode and the development database fallback (23.9).
- Retention now exists for signature/voice/marketing receipts, terminal `jobs`/`job_logs` and orphan stream rows,
  each terminal-state, age- and batch-bounded (migration 094, 23.7). `audit_log` is deliberately excluded and its
  24-month, export-before-purge expectation is documented.
- Job views deep-redact secret-shaped keys; failed jobs can be retried or discarded through the API (23.7).
- Security events (denied access, lockouts, failed logins, CSRF refusals, webhook signature rejections, replays,
  key rotation) are emitted with correlation ids and counts only, and surface in the administrator operations
  snapshot (23.8).
- Incident-response, deployment-baseline, tenancy and distribution-compliance documents exist (23.9).

## 2. Migration requirements

Apply migrations **before** starting the new code (`pnpm db:migrate`; the API also applies them at boot). All
Phase 23 migrations are additive and forward-only:

| Migration | Change |
|---|---|
| `089_auth_login_attempts.sql` | Failed-login counters that drive the lockout. |
| `090_auth_password_resets.sql` | Single-use password-reset tokens. |
| `091_session_hardening.sql` | Session families, idle/absolute expiry, revocation metadata. |
| `092_api_key_lifecycle.sql` | API-key scopes, `last_used_at`, IP/CIDR restrictions, rotation lineage. |
| `093_phase23_oidc_signin.sql` | Single-use OIDC state/nonce rows. |
| `094_phase23_retention_schedules.sql` | Seeds five retention schedules (no data change). |

Do not roll back by dropping columns or tables. A failed migration is a stop-the-line event.

## 3. Operational actions before any pilot

1. Set `DATABASE_URL`, `JWT_SECRET`, `ENCRYPTION_KEY`, `CORS_ORIGINS` and `EXTENSION_TRUST_MODE=enforce` from the
   deployment secret store. `NODE_ENV=production` activates the boot guards, so placeholders fail at startup.
2. Configure `MAIL_TRANSPORT` (default `none`) before using password reset or any email path; review
   `docs/runbooks/security-incident-response.md` and `docs/security/deployment-baseline.md`.
3. Install the encrypted off-host backup and run a restore drill — **both are still blocked** (G80/G81).
4. If OIDC is used, register the exact redirect URI and set `OIDC_PROFILES`; without it the sign-in screen offers
   only the password form.
5. Review the exception register and obtain owner signatures for the live High/Critical rows.

## 4. Release decision

**NO-GO for production.** The DB-free gate and the focused security suites pass; the blockers are operational and
legal, not test failures: G80/G81 (backup and restore), the missing `LICENSE`/distribution decision, and unsigned
High/Critical exceptions. A conditional alpha/pilot GO is defined in the release review §8.

## 5. Known limitations

- No metrics/tracing exporter; security counters are process-local (G77).
- CI is a nightly integrity check, not a PR gate (G78, owner decision D3).
- Authorization has no DB-free assertion; the ACL/BOLA suites stay sandbox-only (G92).
- The SPA keeps the short-lived access token in `localStorage`; a browser spec pins the bound but does not remove
  the exposure.
- Worker BPM/workflow writes are system-scoped and bypass the API ACL layer by design (G89).
- The served OpenAPI document is a route inventory (no DTO schemas) and is unauthenticated (G1, G90).
- Multi-tenancy is absent by decision; tenant isolation is deployment separation only.
- Dependency auditing and extension signing remain release-checklist items (G97, G98).
