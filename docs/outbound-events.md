# Outbound events and webhook deliveries (Phase 24.8)

The generic outbound connector is the `webhook-integration` extension package
(`modules/webhook-integration`). It is opt-in: an administrator installs it through
`POST /api/v1/Extension/action/install`, its own migration creates the endpoint and delivery
ledger tables, and **no outbound request is ever made until an endpoint is registered**. The
administration API lives under `/api/v1/WebhookEndpoint` and is documented in
`api-spec/webhook-endpoints.yaml`.

## D6 decision

No new CLI and no GraphQL endpoint. Integrators extend a single-tenant installation through
`packages/extension-sdk`, the `webhook-integration` module and the `api-spec/` registry. A
metadata `plan/apply` CLI was considered and deferred: the extension SDK + manifest +
`api-spec` tooling already cover the declarative surface, and a second tooling path would
duplicate it (see `plans/PLAN_Phase_24_Product_Completion.md` D6).

## Event catalogue

Endpoints subscribe to the kernel domain events emitted for every generic record mutation
(`packages/core/src/domain-events`, produced by `EntityEventHookService` inside the mutation
transaction via the outbox):

| Event type | Emitted when |
|---|---|
| `entity.created` | a record is created |
| `entity.updated` | a record is updated |
| `entity.deleted` | a record is soft-deleted |
| `entity.restored` | a soft-deleted record is restored |

`SUPPORTED_EVENTS` in `modules/webhook-integration/src/shared.ts` is the subscribable list —
it is pinned to `DOMAIN_EVENT_TYPES` by `apps/api/test/webhook-outbound-contract.test.ts`, so
a new kernel event type fails the contract test until it is deliberately added here.

An endpoint's `events` array must name the types it wants; there is no wildcard. The worker
subscriber fans every domain event out to `webhook.deliver`, and the job delivers only to
enabled endpoints whose `events` list contains the event type.

## Delivery envelope

Each delivery is `POST <endpoint.url>` with `content-type: application/json` and this body:

```json
{
  "id": "entity.updated:acc-1",
  "eventType": "entity.updated",
  "payload": {
    "entityType": "Account",
    "entityId": "acc-1",
    "changed": ["name", "industry"],
    "userId": "user-1",
    "version": 3
  }
}
```

- `id` is `<eventType>:<entityId>` — stable per record mutation, usable as a dedup key.
- `payload.entityType`/`entityId` identify the record; fetch current state through the REST
  API rather than trusting the event payload as a snapshot.
- `payload.changed` lists the field names that changed (empty for delete/restore).
- `payload.userId` is the acting user, or `null` for system writes.
- `payload.version` is the **record** version after the mutation, not a payload-schema
  version. Treat the envelope fields above as the versioned contract; if they change, the
  change is announced here and in the test suite.

Headers:

| Header | Meaning |
|---|---|
| `x-caro-event` | the event type, e.g. `entity.updated` |
| `x-caro-delivery` | ISO-8601 timestamp of this attempt |
| `x-caro-signature` | `sha256=<hex>` — HMAC-SHA256 of the **exact request body bytes**, keyed with the endpoint secret |
| `user-agent` | `CaroCRM-Webhook/1.0` |

The secret is generated by the administrator at endpoint creation, stored AES-256-GCM
(`ENCRYPTION_KEY`), and never returned by the API (`hasSecret` only).

## Verifying a delivery (receiver side)

```js
import { createHmac, timingSafeEqual } from 'node:crypto';

function verify(rawBody, headers, secret, { windowMs = 5 * 60 * 1000, now = Date.now() } = {}) {
  const expected = 'sha256=' + createHmac('sha256', secret).update(rawBody).digest('hex');
  const got = headers['x-caro-signature'] ?? '';
  if (got.length !== expected.length || !timingSafeEqual(Buffer.from(got), Buffer.from(expected))) {
    return false;
  }
  const sentAt = Date.parse(headers['x-caro-delivery'] ?? '');
  return Number.isFinite(sentAt) && Math.abs(now - sentAt) <= windowMs;
}
```

Verify the signature over the **raw bytes** before parsing JSON, and reject deliveries whose
`x-caro-delivery` is older than your replay window (5 minutes is the documented default).
`webhook-outbound-contract.test.ts` pins the signature format and timestamp freshness.

## Retry, ledger and failure semantics

- Delivery runs in the worker as the `webhook.deliver` BullMQ job (10 s timeout per endpoint,
  SSRF re-checked on every attempt, redirects not followed). Nothing is sent from the API
  request path.
- **Transport failure** (DNS, connect, timeout): the attempt is ledgered `failed` and the
  error is re-thrown so BullMQ retries the job with backoff.
- **Any HTTP response**, including 4xx and 5xx: the attempt is ledgered `failed` with the
  response code and the job completes — an answered request is not retried automatically.
  Fix the receiver or the endpoint and re-drive by re-saving the record.
- Every attempt writes one row to `extension_webhook_deliveries` (endpoint, event type,
  payload, status, attempts, response code, error). Administrators read the newest 100 via
  `GET /api/v1/WebhookEndpoint/:id/deliveries`; `DELETE` on an endpoint removes its ledger
  rows with it.
- Destination safety (PLAN §48): `https` only, no embedded credentials, and every resolved
  address must be public — loopback, RFC1918, link-local and cloud-metadata ranges are
  refused at registration **and** again per attempt.

## Single-tenant rule for extensions

One installation serves one organisation. An extension package must never process another
customer's data, must not assume a tenant id, and must run with `EXTENSION_TRUST_MODE=enforce`
and signed packages in production (Phase 23.6, G98). Extensions receive only the `ExtensionApi`
facade (database handle, job queue, scoped config, logger) — never the Nest container — so they
cannot reach kernel internals or bypass ACL. The same rule covers outbound webhooks: an
endpoint receives this installation's events only.

## Typed client

`packages/api-client` is the typed client generated from `api-spec/` (Phase 24.4). It currently
ships schema-backed operations for the session surface (`authentication.*`, `session.*`) and is
consumed by `apps/web/src/api/types.ts`; extending `operationId`/`requestSchema`/
`responseSchema` coverage to more groups is incremental work, not a second pipeline. The
`/api/v1/WebhookEndpoint` administration API is a plain REST surface documented in
`api-spec/webhook-endpoints.yaml`; receivers verify deliveries with the contract above — no
GraphQL endpoint or second webhook framework exists.
